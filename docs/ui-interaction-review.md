# UI 交互评审规范

本规范适用于所有用户可见界面的设计、实现、重构和验收。

核心原则：**评审对象是用户在真实窗口中完成的任务，不是单个组件，也不是一张好看的快照。**

## 1. 先定义页面任务

开始设计或评审前，先写清：

- 页面唯一的主要任务是什么？
- 当前状态下，用户最合理的下一步是什么？
- 哪个操作是主操作，哪些只是辅助操作？
- 哪些信息或控件在当前状态下没有价值？

无法用一句话说明页面任务时，先修正信息架构，不做视觉润色。

## 2. 按正确顺序评审

严格按以下顺序检查，前一层不成立时，不进入下一层：

1. **任务焦点**：用户是否能在三秒内判断页面用途和下一步？
2. **信息架构**：每个栏位、分区和层级此刻是否提供价值？
3. **状态语义**：空、加载、错误、选中和编辑状态是否给出正确操作？
4. **交互行为**：鼠标、键盘、焦点、滚动、取消和破坏性操作是否符合平台习惯？
5. **视觉表现**：颜色、字体、间距、边框和层级是否符合批准的视觉基调？

视觉还原不能抵消任务或结构问题。

## 3. 必测状态矩阵

任何重要界面至少覆盖：

| 维度 | 状态 |
| --- | --- |
| 数据量 | 空、1 条、典型数量、极端数量 |
| 窗口 | 最小可用、常用、宽屏 |
| 生命周期 | 加载、成功、失败 |
| 选择 | 未选中、选中、切换选择 |
| 编辑 | 打开、输入、取消、完成 |
| 系统 | 明暗模式、键盘导航、滚动 |

不能到达的状态必须在报告中明确列为未验证，不能默认为通过。

## 4. 阻断规则

出现以下任一问题，界面不得判定为完成：

- 当前没有内容价值的栏位仍永久占据空间。
- 同一屏出现相互竞争或重复的空状态。
- 空状态没有一个明确、就近的下一步操作。
- 没有有效操作对象时，仍展示可执行控件。
- 调试、统计或后台运行信息主导工具栏或页面层级。
- 根视图未填满可用区域，导致内容被意外居中、漂浮或错位。
- 最小窗口下，关键标题或主操作被截断到无法识别。
- 极端数据量把卡片、开关或菜单扩展成不可管理的墙。
- 破坏性操作缺少清晰标识、确认或可恢复路径。
- 只能用鼠标完成本应支持键盘的核心流程。

## 5. 空状态要求

空状态必须回答三个问题：

1. 这里为什么为空？
2. 用户接下来能做什么？
3. 哪个按钮可以立即开始？

空状态中的主操作应靠近说明文本。不要只在远处工具栏保留一个弱入口，也不要展示依赖现有数据的操作。

## 6. 栏位和检查器

新增或保留栏位前必须证明它在当前状态下有即时价值：

- 没有选择对象时，详情栏应收起或提供独立且必要的内容。
- 详情栏不能只重复主栏的空状态。
- 窄窗口优先保证主任务；辅助栏位应先折叠。
- 三栏布局必须验证空数据、未选中和最小窗口，不能只验证满数据宽屏。

## 7. 真实交互验收

每轮 UI 修改后：

1. 启动真实应用，不以 Preview 代替。
2. 使用真实或具代表性的数据完成核心任务。
3. 在同一组固定窗口尺寸下检查前后结果。
4. 实际操作打开、选择、输入、取消和完成。
5. 检查键盘焦点、滚动和破坏性操作边界。
6. 保存真实窗口截图作为主要证据。

组件 Preview、离屏快照和单元测试可以补充证据，但不能证明完整界面成立。

## 8. 视觉判定

视觉验收分别记录两项结果，不取平均掩盖问题：

- **视觉还原**：是否符合批准的参考、主题和平台风格。
- **交互质量**：任务焦点、层级、状态、可发现性和窗口适应性是否成立。

任一项失败，整体结论就是 `revise`。判定必须基于与参考一致的页面状态、数据和窗口尺寸。

## 9. 删除式评审

完成前再问一次：

- 哪一栏可以删或按需出现？
- 哪段说明可以删？
- 哪个按钮在当前状态下没有意义？
- 哪两个状态可以合并？
- 哪条信息只对开发者有用？

优先删除无价值元素，不用更多组件掩盖结构问题。

## 已吸收的教训

- 不用组件快照代替完整产品窗口。
- 不用视觉风格一致代替交互质量。
- 不用测试通过代替界面成立。
- 用户指出的“看起来不对”是需要复现和定位的证据，不是需要辩解的主观意见。
